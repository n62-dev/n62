# F-Droid draft

`dev.n62.calc.yml` is a draft of the fdroiddata recipe. It is **never submitted**; the application id `dev.n62.calc` is final (owner, 2026-11-05, decisions.md "The name N62").

How it builds, and how it differs from `./build.sh`:
- `build.sh` builds the engine in a podman container (P2). The F-Droid build VM cannot nest that, so the recipe installs the **same Debian `emscripten` package** (3.1.69+dfsg-3 in trixie) and runs the same scripts with `EMSDK_DIR=system`. F-Droid then builds the APK with its own Gradle (`gradle: yes`) and signs it itself.
- Source tarballs (Giac, GMP, MPFR, GSL, libqalculate) are downloaded and SHA-256-checked by the scripts, and `npm ci` downloads packages. F-Droid builds are normally offline after `prebuild`, so check this (and a `srclibs` rework) before submitting.
- **libqalculate** (`engine/qalc/build-wasm.sh`, docs/04 7.1) is no longer part of `./build.sh` (A21): the Find index reads its numbers from the checked-in `find/factors.yaml` and only the names and titles from the libqalculate 5.13.1 tarball's XML (downloaded and SHA-256-checked by the generator). The script stays for developers: `tools/find-index/refresh-factors.mjs` builds on it and prints the difference to the file. Nothing of qalc's code goes into the APK.
- **The recipe keeps its libxml2 and libqalculate builds** (owner, 2026-11-02, decisions.md P22): F-Droid is not asked to accept checked-in derived data. Its `build:` block runs `engine/qalc/build-wasm.sh dev`, then `refresh-factors.mjs`, which fails on any difference to `find/factors.yaml` (A60), so F-Droid's own build proves the file. Our other builds read the file and build no qalc.
- The container builds of the engine and of libqalculate are byte-reproducible between runs. The system-emscripten build on the VM should match; verify before claiming reproducible builds.
- **Nothing is built in `prebuild` (A97).** F-Droid's build metadata reference: prebuild runs "before the build takes place. Note that nothing should be built during this prebuild phase"; `build` "runs during the actual build phase ... Use this only for actions that do actual building." fdroidserver 2.4.5 (`build.py`) scans the source between the two and joins each list with `; `, run by `bash -e -u -o pipefail -x -c` in the build's subdir. So `prebuild` only fetches: `engine/giac/build-wasm.sh --fetch-only` and `engine/qalc/build-wasm.sh dev --fetch-only` (the SHA-256-checked downloads, nothing compiled, no compiler needed) and `npm ci`; the engine builds, the factors check, `npm run index`, `npm run build` and `cap sync` are the `build:` block. The tarballs go to `/tmp/n62-dl` and `/tmp/n62-qalc-dl`, outside the scanned tree. The source scan (`scan_source`) flags 7 files in `app/node_modules/` after `npm ci` (five gzip archives in `@capacitor/cli/assets`, `playwright-core/lib/webp_codec.wasm`, `jsxgraph/distrib/jsxcompressor.zip`; fdroidserver 2.4.5 on a clean `git archive`, 2026-11-09), and `build.py` then stops with "Can't build due to 7 errors while scanning". So the recipe lists `scandelete: app/node_modules/`: it removes only the files the scanner flags (`scanner.py`, `handleproblem` calls `removeproblem`, which removes that one file), not the directory, so Capacitor's Android modules (`capacitor.settings.gradle`) stay; 57 of the 62 Capacitor recipes in fdroiddata list `node_modules` there. `scanignore` holds `app/node_modules/@capacitor/cli/assets/capacitor-cordova-android-plugins.tar.gz`: `npx cap sync android` unpacks `android/capacitor-cordova-android-plugins` (gitignored) from it and fails ENOENT when it is deleted. With both, the count is 0 and `cap sync` passes (A97f1). The fields stand in the order `fdroid rewritemeta` writes (sudo, gradle, prebuild, scanignore, scandelete, build), because fdroiddata's CI runs it and fails on any difference. The reference says nothing about network access in either phase, so the recipe does not rely on it after `prebuild` (everything `build` needs is fetched before); whether the scanner flags a file in `node_modules/` is not known before the first real build.
- **The compiler is pinned (A96):** the recipe installs `emscripten=3.1.69+dfsg-3` and exports `EMSCRIPTEN_PKG_VERSION`; `build-wasm.sh` with `EMSDK_DIR=system` stops when the system `emcc`'s version differs from that value's upstream part. The build VM is Debian trixie (fdroiddata's CI job `fdroid build` runs `registry.gitlab.com/fdroid/fdroidserver:buildserver-trixie`, and fdroidserver's `buildserver/Vagrantfile` uses `debian/trixie64`; checked 2026-11-09), where `emscripten` is 3.1.69+dfsg-3 (packages.debian.org/trixie/emscripten). `app/scripts/fdroid-recipe.test.ts` compares the recipe with `build-wasm-release.sh`.
- The submission steps (fdroiddata merge request, IzzyOnDroid request): [SUBMIT.md](SUBMIT.md).
- Open items before a real submission: the release tag v0.1.0 (the owner pushes it; `tools/check-version.sh v0.1.0` checks the files).

- Checked 2026-10-11 with fdroidserver 2.4.5 (pip, venv): `fdroid readmeta` parses the recipe. `fdroid lint` only complains that the category is unknown, because a scratch repo has no `config/categories.yml`; the real fdroiddata uses "Science & Education" in 534 recipes. A real `fdroid build` needs the build-server VM (vagrant/KVM image), which is not set up here, so the recipe is untested end to end.
