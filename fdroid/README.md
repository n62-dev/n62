# F-Droid draft

`dev.n62.calc.yml` is a draft of the fdroiddata recipe. It is **never submitted**; the application id `dev.n62.calc` is final (owner, 2026-11-05, decisions.md "The name N62").

How it builds, and how it differs from `./build.sh`:
- `build.sh` builds the engine in a podman container (P2). The F-Droid build VM cannot nest that, so the recipe installs the **same Debian `emscripten` package** (3.1.69+dfsg-3 in trixie) and runs the same scripts with `EMSDK_DIR=system`. F-Droid then builds the APK with its own Gradle (`gradle: yes`) and signs it with its own key: the recipe asks for no Reproducible Build (A158, owner 2026-11-15), so it has no APK to compare against and no allowed signing key.
- Source tarballs (Giac, GMP, MPFR, GSL, libqalculate) are downloaded and SHA-256-checked by the scripts, and `npm ci` downloads packages. F-Droid builds are normally offline after `prebuild`, so check this (and a `srclibs` rework) before submitting.
- **libqalculate** (`engine/qalc/build-wasm.sh`, docs/04 7.1) is no longer part of `./build.sh` (A21): the Find index reads its numbers from the checked-in `find/factors.yaml` and only the names and titles from the libqalculate 5.13.1 tarball's XML (downloaded and SHA-256-checked by the generator). The script stays for developers: `tools/find-index/refresh-factors.mjs` builds on it and prints the difference to the file. Nothing of qalc's code goes into the APK.
- **The recipe keeps its libxml2 and libqalculate builds** (owner, 2026-11-02, decisions.md P22): F-Droid is not asked to accept checked-in derived data. Its `build:` block runs `engine/qalc/build-wasm.sh dev`, then `refresh-factors.mjs`, which fails on any difference to `find/factors.yaml` (A60), so F-Droid's own build proves the file. Our other builds read the file and build no qalc.
- The container builds of libqalculate are byte-reproducible between runs, and so is the release engine (the same container build, run twice, gave the same bytes).
- **The recipe's engine does not match the release engine (A145, measured 2026-11-14; `tools/probes/fdroid-bits.sh`; verdict `FDROID BITS: differ`).** The probe builds the engine in the pinned `debian:trixie` image with the recipe's apt line and `EMSDK_DIR=system EMSCRIPTEN_PKG_VERSION=3.1.69+dfsg-3`, against the release build (`build-wasm-release.sh`: root, `/src`, `setarch -R`, `JOBS=8`). `giac.mjs` is the same in every build (`c940c2ba237e…`); `giac.wasm` (59 objects):
  - release: `1756b82c44e5…` (twice, identical);
  - the recipe as written (user vagrant, `/home/vagrant/build/dev.n62.calc`, no `setarch`): `bbbf1e656af5…`, 9 objects differ;
  - the same under `setarch "$(uname -m)" -R` (`--security-opt seccomp=unconfined`): `1f331d04bc7c…` (twice, identical), 12 objects differ.
  - Causes: (1) without `setarch -R` the clang objects change with address-space randomisation (recipe against the `setarch` build, everything else equal). (2) `setarch -R true` fails under the container's default seccomp profile (podman 4.9.3: "failed to set personality to x86_64: Function not implemented"); fdroiddata's CI runs `fdroid build` in a container, which was not tried here, so the recipe does not run under `setarch`. (3) Even under `setarch -R` the bits depend on the tree's path: root, `/src`, `setarch`, the release's apt packages and `JOBS=8` give the release bytes exactly (the probe is faithful); with only `JOBS` unset or only the user vagrant they stay identical; with only the path `/home/vagrant/build/dev.n62.calc` 12 objects differ (derive, ifactor, intg, lin, modpoly, optimization, permu, plot, plot3d, prog, usual, vecteur); with only the recipe's apt line (its `npm` adds 548 packages) 3 differ (prog, usual, vecteur). An extra 1000-byte environment variable changes nothing. The wasm holds no path string (Giac's objects are compiled with relative file names), so `-ffile-prefix-map` would not help; the compiler's own output depends on where the tree and the packages sit (cause not isolated).
  - The APK as a whole (Vite bundle, Gradle output) is still uncompared. The owner's choice (2026-11-15): the Reproducible Builds box stays unticked at v0.1.0, F-Droid signs with its own key (A158).
- **Nothing is built in `prebuild` (A97).** F-Droid's build metadata reference: prebuild runs "before the build takes place. Note that nothing should be built during this prebuild phase"; `build` "runs during the actual build phase ... Use this only for actions that do actual building." fdroidserver 2.4.5 (`build.py`) scans the source between the two and joins each list with `; `, run by `bash -e -u -o pipefail -x -c` in the build's subdir. So `prebuild` only fetches: `engine/giac/build-wasm.sh --fetch-only` and `engine/qalc/build-wasm.sh dev --fetch-only` (the SHA-256-checked downloads, nothing compiled, no compiler needed) and `npm ci`; the engine builds, the factors check, `npm run index`, `npm run build` and `cap sync` are the `build:` block. The tarballs go to `/tmp/n62-dl` and `/tmp/n62-qalc-dl`, outside the scanned tree. The source scan (`scan_source`) flags 7 files in `app/node_modules/` after `npm ci` (five gzip archives in `@capacitor/cli/assets`, `playwright-core/lib/webp_codec.wasm`, `jsxgraph/distrib/jsxcompressor.zip`; fdroidserver 2.4.5 on a clean `git archive`, 2026-11-09), and `build.py` then stops with "Can't build due to 7 errors while scanning". So the recipe lists `scandelete: app/node_modules/`: it removes only the files the scanner flags (`scanner.py`, `handleproblem` calls `removeproblem`, which removes that one file), not the directory, so Capacitor's Android modules (`capacitor.settings.gradle`) stay; 57 of the 62 Capacitor recipes in fdroiddata list `node_modules` there. `scanignore` holds `app/node_modules/@capacitor/cli/assets/capacitor-cordova-android-plugins.tar.gz`: `npx cap sync android` unpacks `android/capacitor-cordova-android-plugins` (gitignored) from it and fails ENOENT when it is deleted. With both, the count is 0 and `cap sync` passes (A97f1). The fields stand in the order `fdroid rewritemeta` writes (sudo, gradle, prebuild, scanignore, scandelete, build), because fdroiddata's CI runs it and fails on any difference. The reference says nothing about network access in either phase, so the recipe does not rely on it after `prebuild` (everything `build` needs is fetched before).
- **The compiler is pinned (A96):** the recipe installs `emscripten=3.1.69+dfsg-3` and exports `EMSCRIPTEN_PKG_VERSION`; `build-wasm.sh` with `EMSDK_DIR=system` stops when the system `emcc`'s version differs from that value's upstream part. The build VM is Debian trixie (fdroiddata's CI job `fdroid build` runs `registry.gitlab.com/fdroid/fdroidserver:buildserver-trixie`, and fdroidserver's `buildserver/Vagrantfile` uses `debian/trixie64`; checked 2026-11-09), where `emscripten` is 3.1.69+dfsg-3 (packages.debian.org/trixie/emscripten). `app/scripts/fdroid-recipe.test.ts` compares the recipe with `build-wasm-release.sh`.

- Open items before a real submission: the release tag v0.1.0 (the owner pushes it; `tools/check-version.sh v0.1.0` checks the files).

- Checked 2026-10-11 with fdroidserver 2.4.5 (pip, venv): `fdroid readmeta` parses the recipe. `fdroid lint` only complains that the category is unknown, because a scratch repo has no `config/categories.yml`; the real fdroiddata uses "Science & Education" in 534 recipes. A real `fdroid build` needs the build-server VM (vagrant/KVM image), which is not set up here, so the recipe is untested end to end.
