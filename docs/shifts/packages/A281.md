### annabell, A281: e2e gives each test its own clipboard; the shared lock stays only where the real clipboard is the subject, branch `p1/annabell-pageclip`
**Lane:** B, Sonnet. **Starts when:** at once. Waste (e2e is 53 % of all check time and a third of it is one lock). **Found by:** A278 (report commit 935cdacd, merged d8b33c05; owner, 2026-11-26: write it).
**Why:** `useClipboardLock()` (app/test/helpers.ts, about line 417; R74f1, F202) is a FIFO ticket lock across every Playwright worker, because Chromium's system clipboard is one for the whole machine. 31 spec files (475 tests, core.spec.ts among them) hold it, so they run one test at a time while the other workers idle. A278 measured, dev server, 16 workers, quiet host: those 31 files 457 s with the lock and 155 s with it turned into a no-op (469 of 475 pass; the 6 that fail are clipboard-lock.spec.ts's own tests, which read the shared clipboard on purpose); whole-suite shard 1/3 248.1 s against 166.7 s (-33 %). Extrapolated, not measured: the pipeline's e2e round from a median 676 s to about 450 s. It is also why A126 saw 8 and 16 workers equally fast.
**Read:** app/test/helpers.ts (`setClipboard`, the paste helpers about line 145 to 173, the lock from line 283, `withClipboardLock`, `useClipboardLock`, `open` or whatever opens a page); app/test/clipboard-lock.spec.ts; the 31 files (`grep -l useClipboardLock app/test`); app/src/clipboard/ (what the app calls: `navigator.clipboard.writeText`, `readText`, `write`, a `paste` event); A278's report (`git log -1 --format=%b 935cdacd`).
1. **Tests first, failing on phase-1:**
   - a new spec (or cases in clipboard-lock.spec.ts) with two tests in two workers at the same time, each writing a different text through the app (Copy of a row) and reading it back through the app (Paste): each gets its own text back, with no lock held. Red on phase-1 without the lock (they see each other's text); green with the per-page clipboard.
   - `useClipboardLock` is called by at most the files that test the real system clipboard on purpose; a test fails when a spec file calls it without a one-line reason comment beside the call (a short list kept in helpers.ts, one place).
   **Controls (unchanged):** every one of the 31 files passes, now without the lock (only the clipboard-lock tests that are about the shared clipboard keep it); the core list (`npm run test:core`); `bash scripts/pipeline.test.sh` is untouched (no pipeline change).
2. **The change:**
   - An init script (`page.addInitScript` in the helper that opens a page, or a fixture every spec gets) replaces `navigator.clipboard.writeText`, `readText`, `write` and `read` with an in-page store per browser context, and keeps the `paste` event path working from that store. The app code is not changed; nothing of this ships (test only).
   - `setClipboard` and the read helpers use that store. The 31 files drop `useClipboardLock()`; the lock and its tickets stay for the files that keep it.
   - Keep at least one test that runs a real Copy and a real Paste through Chromium's system clipboard under the lock (the app's real permission and API path), and say which in the report.
   - Then, if the store lets them, `copy.spec.ts` and `decimalcomma.spec.ts` (describe mode serial, 25 and 24 tests; they end last even without the lock) lose their serial mode where a test does not depend on the one before; leave it where it does, and say so.
3. **Docs:** none outside the code (no current doc explains the lock); the comment above the lock in helpers.ts says what is left on it and why (R74f1, A281).
