### annabell, A258: a rerun after a usage limit skips the worker that already finished, branch `p1/annabell-limitresume`
**Lane:** the one lane after the stop, first (owner, 2026-11-17: Pro). Sonnet, audit Opus (every run's path). **Starts when:** –.

**Why** (the Pro plan from 2026-11-17 16:46 has a twentieth of Ultra's usage, so the CLI's five-hour limit will stop runs often): `agent_end` (`scripts/pipeline.sh`, the LIMIT line after `own_wait`) exits 75 at a usage limit in any agent, the worker, a fix round, a conflict resolve or the audit. night.sh waits and runs the same command again. That rerun resumes the branch (the worktree block after "The worker's worktree, fresh from phase-1 or resumed") and then always starts a fresh worker (`run_agent "pl-$n-$agent"` under `if [[ $nowork -eq 0 ]]`), even when the worker had finished and the limit came later. The fresh worker reads its bundle, the rules and the code again, which costs a whole worker context to find out that there is nothing left to do.

**Read:** `scripts/pipeline.sh` (`agent_end`, the resume block, the `nowork` path and A10's review-only run, `fix_round`, `audit_start`); `scripts/pipeline.test.sh` (the claude stand-in and how it fakes a LIMIT); rules section 4 (A10, A121).

1. **Tests first** (`scripts/pipeline.test.sh`, failing on phase-1):
   - a run whose worker finishes and commits and whose audit then hits a LIMIT exits 75; the same command run again starts no worker (no `pl-<n>-<agent>` call in the stand-in's call list), runs the checks and the audit, and merges;

   - a marker from an older run of another id, or of the same id on another branch, changes nothing;

A RESULT line other than LIMIT removes the marker. Nothing else changes: the round count starts again at 0, as for a review-only run.
