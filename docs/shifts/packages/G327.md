### gorge, G327: a start that failed to load never counts against the stored definitions, branch `p1/gorge-loadcount`
**Lane:** A, night-safe, Opus (the definitions log: stored data every later input reads). **Starts when:** R284 merged (both near the engine's start and the start chunk). Before the tag.
**Why:** (F222, G318's report, Opus pass 141; checked by reading the code on `b902cdef`, the test below is the probe) G19 leaves the stored definitions out of the replay after two failed starts, because a definition that crashes the engine would crash it on every launch. Since G318 a failed start is classed: `crash`, `memory` or `load` (`app/src/engine/workerEngine.ts:334`, `:346`; `dead.ts` `startDead`). A `load` failure is a wasm or worker script that did not arrive or instantiate: the log never ran, yet it is counted as the log's.
- `restart` (`workerEngine.ts:313-318`): with a stored log, a failed start calls `beginAttempt` (`:204-206`), which writes the stored count (`saveStarts`, `:199-200`); at `MAX_FAILED_STARTS` (2, `:50`) it calls `leaveOut(this.stored())`. The count is also read at the next launch (`:164-167`, `:133-138`).
- So two load failures in a row (a flaky PWA update, a webview that could not fetch `giac.wasm`) leave every stored variable and function out of the engine at the next start that works: Memory still lists them, the app shows its safe-start note (`safeStart`, `app/src/calc/port.ts:106`), and an input that reads one gets an unknown name. The user did nothing wrong and the definitions were never tried.
- G318's in-memory stop after two failed starts with no log (`:314`) is right for load failures and stays.
**Read:** line numbers as of `b902cdef`; recheck at start. `app/src/engine/workerEngine.ts:38-60, 105-220, 300-350`; `app/src/engine/dead.ts` (`startDead`); `app/src/engine/workerEngine.startcap.test.ts` (its `StartWorker` stand-in and cases); `app/src/engine/workerEngine.test.ts:415-440` (the stored count's store); `app/src/calc/index.ts:1-20`; docs/04 section 3.4 (the log).
1. **Tests first, failing on phase-1** (controls say so), in `app/src/engine/workerEngine.startcap.test.ts` (stand-in workers, a store with one stored definition):
   - two inits that fail with `dead: "load"`, then a launch whose init works: the stored count stays 0 after each, nothing is left out, and the working launch replays the definition (`define` reaches the worker);
   - the same with a worker error before ready classed as a load error (no message);
   - G318 kept: with the log, two load failures in one launch stop the engine (ready() rejects with EngineLoadError, at most 3 workers), and a Cancel starts one fresh attempt.
   - Controls (pass today): two inits that fail with `dead: "crash"` (and two with `memory`) still leave the log out on the next launch, as G19 says; a crash after ready restarts and replays as before.
2. **The change:** a failed start counts toward the stored G19 count only when it is not a load failure; a load failure counts in memory (`attempts`) toward G318's stop, with or without a log, and never calls `leaveOut`. No new state, no new message.
**Done when:** the tests pass and all but the controls failed on phase-1; `FIND_INDEX=required npm test`, e2e and the core list pass; `npm run size` passes: `workerEngine.ts` is in the start chunk (`calc/index.ts:3`), whose pin R284f1 sets at its measure plus 0.05 kB (pass 143), so the change stays a condition; over the pin it raises it as docs/04 8.3 says, and the report gives the start chunk's gzip size before and after; no pin is raised without its reason.
