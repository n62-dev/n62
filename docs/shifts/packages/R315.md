### ron, R315: the unit view reads a stored name with a unit as a result chip with its slot, branch `p1/ron-nameslot`
**Lane:** A, Opus (units entry). **Starts when:** G371 merged; queued before the freeze (owner, 2026-11-15: the queue holds everything).
**Why:** (night review 2026-11-14, fh-3; the owner's answer 4 of [the note](../../research/night-review-2026-11-14.md) section 6; R53c, `docs/archive/r19-results-and-keys.md` "Named values")
- Today a slot after a name is refused in the unit view (R28 default 3), while a `\res` chip gets a slot filled with its unit (R63, `app/src/input/unitFormula.ts`). Once G371 stores a name's unit and σ, the unit view reads such a name as it reads a result chip: its slot is filled with its unit, and its σ is carried.
- **The slot ids** (sofia's review of the formula-units plan, finding 1, 2026-11-16): a history row keeps its units by slot id (`UnitRow.slots`, `app/src/units/types.ts:259`).
  - **Why not written order:** if a name's slot took its id in written order among the numbers' (as a `\res` slot does, `unitFormula.ts:170-176`), which ids the numbers get would depend on what is stored at the time. Take a row `F·2` saved with `{u1: m}` while F had no unit. Once F is stored with a unit, picking that row would put m on F and leave the 2 without one, silently (the seed wins, `app/src/units/view.ts:130-136`).
  - **The rule:** so the number and `\res` slots keep `u1…uN` in written order, as today, and each name slot takes the ids after them, `u(N+1)…`, in the order the names first appear. R346 (after the tag) keeps the same rule for every name.
