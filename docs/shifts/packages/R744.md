### ron, R744: the layout lock reads only release tags; a pre-release (`v0.1.0-beta.1`) neither pins the lock nor counts as newer than its release, branch `p1/ron-lockprerelease`
**Lane:** the freeze's fix lane, night-safe, Sonnet. **The owner's yes:** none needed: docs/06 3b pins the layout "from the tag" (v0.1.0), and the beta's notes say stored data may still change (release-0.1.0.md, the freeze row). **Starts when:** –; in the fix lane after R743, and **it must merge before `v0.1.0-beta.1` is tagged** (the beta follows it; owner, 2026-11-17), or every layout package still to merge that edits a live lock line (R720's renumbered `home-menu`, R722's `bar:`) fails the lock test against the beta.

**Why:**
- `releaseLock` (`app/src/keyboard/layoutLock.ts:201-215`) takes the first tag of `git tag --list v* --sort=-v:refname` that holds `spec/layout-lock.yaml`, and `layoutLock.test.ts:161-164` fails on any live line of that tag's lock that is missing or edited.
- Git's version sort puts a pre-release **above** its release: `v0.1.0-beta.1` before `v0.1.0` (`tools/probes/history-1117/probe-tagsort.sh`, git on this host). So:
  1. the beta would pin the lock before the tag, and any later edit of a live lock line would have to be written as `moves:`;
  2. after v0.1.0, the test would still compare against the beta's lock, not v0.1.0's, until v0.1.1.

**The result:**
- `releaseLock` skips every tag with a `-` after the version (`/^v\d+\.\d+\.\d+$/` only), so a pre-release never pins and never shadows its release.
- Nothing else changes: no tag exists yet, so the test's result on phase-1 is the same.

**Read:** `app/src/keyboard/layoutLock.ts:195-215`, `layoutLock.test.ts:155-170,400-425`, docs/06 3b (:67), `docs/release-0.1.0.md` (the beta), `tools/check-version.sh` (how it reads a `-` suffix).
