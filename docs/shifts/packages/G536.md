### gorge, G536: Giac's interval of an integer or a float holds the number (patch at `convert_interval`), branch `p1/gorge-intervalpoint`
**Lane:** B, night-safe, Sonnet (a small Giac patch with its canary). **Starts when:** G519 merged (MPFI in the engine); the owner's go on S20.

**Why:**
- **r22's defect D2** ([r22](../../research/r22-mpfi.md) section 3): `convert_interval` turns an integer or a `_REAL` into the point [f, f] with f = `accurate_evalf(g, nbits)`, rounded to nearest, not outward (`prog.cc:8772-8774` of giac 2.1.0, read in `../drafts/2026-11-11-parisse/ref36/giac-2.1.0/src/prog.cc`):
  ```
  if (is_integer(g) || g.type==_REAL){
    gen f=accurate_evalf(g,nbits);
    return eval(gen(makevecteur(f,f),_INTERVAL__VECT),1,contextptr);
  ```
- **What it gives (S20, the spike build):** `convert(10^100+1,interval,40)` is [0.99…97E100 .. 0.99…98E100], below 10^100 + 1; `convert(sin(10^39+1),interval,40)` is [−0.476 .. 0.843] while the value is −0.679034559142… (Giac's own evalf at 80 digits; mpmath agrees). An interval that does not hold its value is a wrong proof: the check would confirm wrong digits with authority (r22 section 6).
- **Rule (rules-core, "Fix Giac bugs at their cause"):** a local cause gets a minimal patch with a canary. G520's literal start (P past the longest integer + 20) hides the defect for literals only; a computed integer inside a form (a `floor`, a `binomial`) still meets it.
- **D1 (`rootof` picks another root) is not patched here:** its cause is unverified (r22 section 5), and G520's allowlist keeps every `rootof` out. The report states it for Parisse's next mail.
