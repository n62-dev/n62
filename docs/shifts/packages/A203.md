### annabell, A203: what one IndexedDB open per call costs on the Tab One, and one kept connection if it costs, branch `p1/annabell-kvopen`
**Lane:** day (device: the Tab One, a measurement build), Sonnet. **Starts when:** after the v0.1.0 tag (0.2), on a day the lanes do not hold the Tab One. Before any package that adds a stored key written per Enter.

**Why:**
- **Night review 2026-11-14, section 5** (carried open in the 11-16 note): "One IndexedDB open per call (`state/storage.ts:82-89`): waits for 50 `kvSet` timed on the Tab One."
- **The code** (as of `5a583f31`): `open()` (`app/src/state/storage.ts:82-89`) calls `indexedDB.open(DB, 1)` and is awaited at the start of every `kvGet` (`:95`) and every `kvPut` (`:131-133`, the body of `kvSet`, `:121-123`). No connection is ever closed. 15 call sites outside tests call `kvSet`; a Home Enter writes at least the history and the session's line (more with sync, R182, and the counters).
- **Two risks, neither measured:** the time of an open on a mid-range WebView per write; and unclosed connections, which block a future `indexedDB.open(DB, 2)` (a schema step) with `onblocked` until they are collected, in this tab and any other tab of the app.

**Read:** line numbers as of `5a583f31`; recheck them at the start.
- `app/src/state/storage.ts` (all of it: `open`, `kvGet`, `kvPut`, `guardWrite`, the writer rule of R95)
- `app/src/bench.ts` (the `?bench=` modes of measurement builds, `VITE_MEASURE=1`), `app/src/main.ts` (where a bench mode starts)
- `tools/device-build.sh --measure`, `tools/README.md` (the device lock)
- `app/src/lazyOnce.ts` (the forget-on-failure rule a kept open must follow)

1. **Measure first (the package's evidence, on phase-1's code):**
   - `?bench=kv` (new, measurement builds only, in `bench.ts`): 50 `kvSet` of a 2 kB value in a row, then 50 of `open()` alone; the median and p95 of each, printed as `bench.ts` prints its others. Run on the Tab One (`tools/device-build.sh --measure --install`) and in desktop Chromium, 3 runs each.
   - **Decision rule, written in the report:** if `open()` alone has a median over 1 ms or a p95 over 5 ms on the Tab One, step 2 runs; else the package ends with the numbers and the backlog line goes (risk 2 then gets its own follow-up id only if a schema step is planned).
2. **Tests first, failing on phase-1** (only when step 2 runs; `app/src/state/storage.test.ts` with the project's own `fakeIdb.ts`, `vi.stubGlobal("indexedDB", …)` as at `:36`; it may need an open counter and a `versionchange` event added):
   - 10 `kvSet` then 10 `kvGet` call `indexedDB.open` once;
   - a failed open is forgotten: the next call opens again (as `lazyOnce`);
   - a `versionchange` event on the kept connection closes it, and the next call opens again;
   - **controls:** the R95 writer rule (a tab that is not the writer writes nothing) and the A50 newer-stamp rule hold unchanged (their existing tests).
3. **The change** (step 2 only): `open()` keeps one connection promise, forgotten on failure and on `onversionchange` (closing the connection) and `onclose`. Nothing else in `storage.ts` changes. The `?bench=kv` mode stays for the next measure.
4. **Docs (the same diff):** docs/04's storage line: "one connection per tab, closed on a version change (A203)" if step 2 runs; else nothing.

**Done when:** the numbers (desktop and Tab One, median and p95, before and, if step 2 ran, after) are in the report; with step 2, the tests pass and the first three failed on phase-1; `FIND_INDEX=required npm test`; the core list passes; `npm run size` with the start chunk within its pin (storage is in the start chunk: a kept promise is a few bytes, measure it).
