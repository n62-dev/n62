### ron, R523: the unit view's mark comes from the value's facts: a ± of zero is no `≈`, branch `p1/ron-unitmark`
**Lane:** A, night-safe, Sonnet (the unit view's mark rule and one evaluator field, with golden rows on both sides). **Starts when:** after the v0.1.0 tag (0.3); after R515 (it moves the stored mark beside `markFor`) and R347 (the unit view draws a formula result, the same function). It sets one field in `units/evaluate.ts`, which G525 and G388 also edit (merge order only).

**Why:**
- **HUNT.md H7 (arch review 2026-11-10), still red at `5a583f31`:** `node tools/probes/unit-result.ts 'pasupm(10,0)*{m}' 'cm'` → `≈ 1000 cm … exact 1000 … σ 0, shown "1000 ± 0"`. The value is exact (10 m is 1000 cm by definition, and σ is 0), yet the mark is `≈`.
- **The cause is one line** (`app/src/units/result.ts:79`): `const mark = m?.mark === "⚠" ? "⚠" : q.unc ? "≈" : (m?.mark ?? "≈")`. Any σ, zero included, makes `≈`; and a value whose facts give no mark (`markOf` null) is drawn `≈` too, where Home draws no mark (docs/04 2.4: a mark says what the facts say).
- **The rest of the rule is right and stays:** a σ above zero claims the value only to σ's last place (R327f1, `withSigmaText`, `:74`), so `≈` or `⚠` there is honest.
- **A σ of zero is not always a σ typed as zero.** Through a step function the GUM σ is 0 from inputs that are uncertain (G143, G159: `floor(pasupm(2.95,0.1))` shows `2 ± 0` with `≈`, `units.yaml:310-329`, `j01`–`j19`); an `=` there would be a false mark. Only a result whose every input σ is zero is exact; `g10` (`pasupm(5,0)*{m}`, `≈ 5 ± 0`, `units.yaml:163`) is that case and changes with this package.
