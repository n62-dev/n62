### ron, R291: the layout lock: a live key layer or a fixed row cannot move unnoticed, branch `p1/ron-layoutlock`
**Lane:** A, Sonnet, no device. **Starts when:** R278, R283, R185, R187, R193, R197 and R131 merged (the last key rows before the freeze).
**Why:** (owner, 2026-11-12: "the layout should stay the same from start of release") from the v0.1.0 tag on nothing that works moves: a key layer or a numbered row that does something keeps doing it, and a later feature grows only into blank space (docs/06 section 3b). Today that holds by memory: `spec/keyboard.yaml` and a sheet's list can be edited in one place and no test objects. The lock makes every such change a second, visible edit that the review and the owner read.
**Read:** docs/06 section 3b (a reserved cell, the growth rule, removals after the tag); docs/05 3.1; `spec/keyboard.yaml`; `app/src/keyboard/keyboard.ts`, `keyboard.test.ts` (how a test alters a copy of the spec). The numbered lists: `app/src/clipboard/actions.svelte.ts` (☰ Home/CAS), `app/src/views/modeSheet.ts` (Mode's rows, Settings' sections), `app/src/apps/shell.svelte.ts` (Apps), the spec's `templates:`, `relations:` and `symbols:` (Tmpl, Shift + 6, Shift + 9), R193's Base sheet, `app/src/views/matrixSheet.ts` (R187).
1. **Tests first, failing on phase-1** (there is no lock):
   - A new `spec/layout-lock.yaml` pins (a) every key layer that is live in the spec, one line each: id, layer, action kind and name (`menu.primary: special menu`); (b) every reserved cell, as `reserved`; (c) for each numbered list the ids of its fixed rows, one line per row, in order.
   - A vitest file (it runs in `npm test`, so in `npm run gate`) compares the lock with the spec and with the lists as the code builds them: it calls the builders and holds no copy. It fails, naming the entry, when a pinned layer's action differs or is gone; when a pinned row is gone, has moved or has a row inserted before it; and when a live layer or a fixed row is not in the lock at all.
   - It passes for growth into blank space, each recorded in the lock: a `reserved` line that turns into a live one, and a row's line appended after the list's last fixed row. Rows of stored content (names, matrices) are not pinned.
   - Each case is a test on an altered copy of the spec or of a list, red first.
2. **A move needs the owner's decision in the file.** A live pinned line is never edited or deleted. A move is a line appended under `moves:`: the entry, the old value, the new value, the version it lands in and the decisions.md entry that holds the owner's yes (the test checks that this entry's title is in decisions.md). The test applies the moves on top of the pinned lines. The new value of a removal is `reserved`.
3. **Against the last release:** where git and a `v*` tag that holds the lock are at hand, the test reads the tag's lock (`git show`) and fails if a live line pinned there is missing, changed or out of its place now. A `reserved` line may have turned live and lines may have been appended. Without git or such a tag it prints "not checked" and passes. So an edit in place cannot hide between two releases.
4. Settings' sections are pinned as the shipped app builds them. The report says in which build `env.userKeys` or `env.data` is absent (`settingsSections`), because a missing section moves the digits of the sections after it.
5. docs/06 section 3b's line on the lock, in place (the report's text).
**Done when:** the tests pass on phase-1's layout as merged; the gate runs the lock and passes; on a scratch copy, one changed key layer turns the lock's test red with the entry's name (the report shows the line); `npm run size` is unchanged (no app code).
